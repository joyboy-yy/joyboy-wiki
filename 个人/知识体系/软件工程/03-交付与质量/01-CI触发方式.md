# CI 触发方式

CI 的触发方式决定验证何时发生、由谁发起、覆盖哪些风险。工程实践中要同时区分自动触发和人工主动触发，避免把“有人点了一次流水线”误认为仓库已经具备稳定质量门禁。

## 自动触发

自动触发由代码仓库、定时器或外部事件驱动，不依赖人工进入流水线页面点击执行。

常见方式：

- **Push 触发**：向指定分支推送提交后自动运行，适合保护主干、开发分支和发布分支。
- **Pull Request / Merge Request 触发**：创建、更新、重新打开 PR/MR 时运行，适合在合并前验证编译、测试、契约和安全扫描。
- **Tag / Release 触发**：创建版本标签或发布对象时运行，适合打包、制品上传和发布前验证。
- **定时触发**：按 cron 或平台计划任务执行，适合每日全量测试、依赖扫描、镜像刷新和长期稳定性检查。
- **路径触发**：只在特定目录或文件变化时运行，适合 monorepo、文档站、前端包或后端模块的局部验证。
- **上游流水线触发**：依赖构建、制品发布或其他 workflow 完成后运行，适合多阶段交付链路。
- **外部事件触发**：通过 webhook、API 或仓库事件触发，适合集成制品库、部署平台和安全系统。

自动触发的核心价值是可重复、可审计、默认发生。只要触发条件覆盖了关键分支和合并路径，团队就能把 CI 结果作为代码进入主干的质量门禁。

## 人工主动触发

人工主动触发由开发者、Reviewer、Release Owner 或运维人员主动发起，适合补充自动门禁无法覆盖的低频场景。

常见方式：

- **手动运行 workflow / pipeline**：在 CI 平台页面选择分支、参数后执行，例如 GitHub Actions 的 `workflow_dispatch`。
- **带参数运行**：人工选择环境、测试范围、版本号、灰度比例或是否执行慢测试，适合发布和高成本验证。
- **重新运行失败任务**：在排除临时网络、缓存、三方服务抖动后重跑失败 job，用于确认是否为偶发失败。
- **审批后继续**：部署到 staging、production 或敏感环境前由人工审批，CI 负责记录审批人、时间和后续执行结果。
- **ChatOps 触发**：通过评论命令或聊天机器人发起，例如 `/retest`、`/deploy staging`，适合把人工意图留在协作上下文里。
- **API / CLI 触发**：通过平台 API 或命令行主动启动流水线，适合本地工具、发布脚本和跨系统编排。

人工触发的核心价值是可控和可选择。它不能替代合并前自动门禁，但可以用于补跑慢测试、临时验证、发布审批和异常恢复。

## 人工主动触发配置

不同 CI 平台的配置语法不同，但核心都是声明一个“允许人工启动”的事件或 job，并把需要人工选择的变量显式暴露出来。

### GitHub Actions

GitHub Actions 使用 `workflow_dispatch` 配置手动触发。配置后，仓库的 Actions 页面会出现 **Run workflow** 按钮，也可以通过 GitHub CLI 或 REST API 触发。

```yaml
name: Manual CI

on:
  workflow_dispatch:
    inputs:
      test_scope:
        description: Test scope
        required: true
        default: smoke
        type: choice
        options:
          - smoke
          - full
      environment:
        description: Target environment
        required: true
        default: staging
        type: choice
        options:
          - staging
          - production

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run selected tests
        run: ./scripts/test.sh "${{ inputs.test_scope }}" "${{ inputs.environment }}"
```

如果还需要代码变更自动触发，可以把 `workflow_dispatch` 和 `push`、`pull_request` 放在同一个 `on` 下，让手动触发复用同一套 job。

```yaml
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
```

### GitLab CI

GitLab CI 可以通过网页上的 **Run pipeline** 主动运行，也可以把某些 job 配成 `when: manual`，让流水线运行到该阶段时等待人工点击。

```yaml
stages:
  - test
  - deploy

test:
  stage: test
  script:
    - ./scripts/test.sh

deploy_staging:
  stage: deploy
  script:
    - ./scripts/deploy.sh staging
  when: manual
  allow_failure: false
```

需要限制手动 job 只在特定分支出现时，可以配合 `rules`。

```yaml
deploy_production:
  stage: deploy
  script:
    - ./scripts/deploy.sh production
  when: manual
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

### Jenkins

Jenkins 的人工主动触发通常来自参数化构建，或者流水线中的 `input` 审批步骤。

参数化构建示例：

```groovy
pipeline {
  agent any

  parameters {
    choice(name: 'TEST_SCOPE', choices: ['smoke', 'full'], description: 'Test scope')
    choice(name: 'TARGET_ENV', choices: ['staging', 'production'], description: 'Target environment')
  }

  stages {
    stage('Test') {
      steps {
        sh "./scripts/test.sh ${params.TEST_SCOPE} ${params.TARGET_ENV}"
      }
    }
  }
}
```

审批后继续示例：

```groovy
pipeline {
  agent any

  stages {
    stage('Test') {
      steps {
        sh './scripts/test.sh smoke staging'
      }
    }

    stage('Deploy Production') {
      steps {
        input message: 'Deploy to production?'
        sh './scripts/deploy.sh production'
      }
    }
  }
}
```

### 配置要点

- 手动入口要暴露必要参数，但不要把高风险参数设计成自由文本优先。
- 发布、生产部署和破坏性任务应加环境保护、审批或权限限制。
- 手动触发和自动触发应调用同一批脚本，例如 `./scripts/test.sh`、`task test` 或 `make test`。
- 参数默认值应选择低风险选项，例如 `smoke`、`staging`，不要默认生产发布或全量破坏性操作。
- 每次人工触发都应能在 CI 平台上追溯触发人、参数、分支、提交和结果。

## 使用原则

- 合并主干前的基础质量检查应优先自动触发，不能依赖人工记得执行。
- 人工触发适合低频、高成本、需要参数或需要审批的流程。
- 自动触发和人工触发应复用同一组脚本或任务入口，避免本地、手动流水线和自动流水线逻辑分叉。
- 触发条件要写清楚分支、路径、事件和跳过规则，否则 CI 结果容易被误读。
- 对 flaky 测试要记录重跑原因，不应把“重跑后通过”直接等同于质量可靠。
- 任务汇报验证结果时，应说明 CI 是自动触发、人工触发，还是只做了本地验证。

## 与自动化执行的关系

自动化工具或 Agent 完成代码变更时，应先识别项目是否存在 CI，以及 CI 是否会覆盖当前变更路径。如果 CI 会在 PR 上自动运行，结果汇报可以把本地验证和待观察的 CI 状态分开说明。如果只有人工触发入口，不能声称“CI 会自动兜底”，而应说明需要由谁、在什么分支、用什么参数主动触发。

结论：自动触发提供默认质量门禁，人工触发提供受控补充能力。两者都属于 CI 能力，但可信度和使用场景不同。
