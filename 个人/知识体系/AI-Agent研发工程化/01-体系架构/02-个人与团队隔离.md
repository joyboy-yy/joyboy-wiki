# 个人与团队隔离

团队资产追求可共享和工具无关，个人资产追求效率和偏好适配。两者混在一起会造成敏感信息泄露、规则争议和工具锁定。

## 边界矩阵

| 内容 | 团队仓库 | 个人本地 |
|---|---|---|
| 架构、模块、命令、数据库约束 | 应提交 | 可缓存但不另立事实 |
| `AGENTS.md` / `CLAUDE.md` | 应提交 | 不做个人定制 |
| 通用测试决策 | 应提交 | 可由个人 Skill 增强 |
| 项目级 Skills | 团队共识后提交 | 试验阶段放本地 |
| MCP 主机、令牌、账号、浏览器 profile | 禁止提交 | 本地配置 |
| 个人工具路由偏好 | 不提交 | 本地 Skill |
| 单元测试或临时 E2E 用例 | 按团队策略 | 本地保存并忽略 |
| 复盘与跨项目方法论 | 可提炼后共享 | 个人知识库 |

## 推荐目录

```text
repo/
  AGENTS.md                 # 团队入口
  PROJECT.md                # 团队项目事实
  TESTING.md                # 团队验证策略
  Taskfile.yml              # 团队执行接口
  .agents/skills/           # 本地或团队 Skill，按 Git 策略决定
  opencode.json             # 本地 MCP 配置，必须忽略敏感信息

~/.config/opencode/         # 用户级 OpenCode 配置
~/.agents/skills/           # 跨项目个人 Skills
~/.codex/                   # Codex 用户配置
```

## 判断规则

- 项目换人后仍必须成立的规则，属于团队。
- 与机器路径、账号、浏览器会话相关的内容，属于个人。
- 只有某个 Agent 客户端能理解的工具说明，优先放个人 Skill。
- 团队 Skill 应描述业务流程或工程判断，不应绑定个人凭据。

## 安全底线

- MCP 配置不得在项目文档中暴露密码、主机私有信息或本机绝对路径。
- 团队文档描述“需要什么能力”，个人配置决定“用哪个工具提供能力”。
- `.gitignore` 是最后防线，不是唯一防线；提交前仍要检查 staged 文件。

## 演进方式

个人 Skill 经多次验证稳定后，可抽象掉本机工具名称，转为团队 Skill。团队规则若只服务某个个人工作习惯，应降级回个人层。
