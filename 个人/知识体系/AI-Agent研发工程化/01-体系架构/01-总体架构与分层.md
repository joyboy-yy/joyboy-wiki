# 总体架构与分层

AI Agent 工程化不是增加更多提示词，而是建立一套职责清晰、能够演进的控制系统。

## 六层模型

| 层级 | 解决的问题 | 典型载体 |
|---|---|---|
| 项目事实层 | 项目是什么、技术栈和边界在哪里 | 源码、依赖清单、配置、`PROJECT.md` |
| 入口约束层 | Agent 一进入项目必须知道什么 | `AGENTS.md`、`CLAUDE.md` |
| 决策能力层 | 何时采用什么流程和工具 | Skills |
| 工具能力层 | 如何访问浏览器、接口、数据库和外部系统 | MCP、CLI、项目脚本 |
| 执行验证层 | 如何修改、测试和证明结果 | `Taskfile.yml`、测试框架、检查脚本 |
| 知识沉淀层 | 如何把结果变成长期资产 | 项目文档、复盘、知识库、模板 |

## 单向依赖

```text
入口约束 -> 指向项目事实和决策能力
决策能力 -> 选择项目命令或工具能力
执行验证 -> 产生结果与风险
知识沉淀 -> 更新事实、规则或方法论
```

避免反向依赖：团队项目文档不应依赖某个个人 Agent、某个本机 MCP 名称或某条私有路径。

## 三种变化频率

- **高频变化**：源码、测试、任务状态。应实时检查，不写死在提示词里。
- **中频变化**：技术栈、模块、端口、命令。由项目清单和 `PROJECT.md` 管理。
- **低频变化**：安全边界、提交规则、测试真实性。放在自动加载入口。

## 架构判断标准

一个规则应放在哪里，可以依次询问：

1. 是否每次任务都必须看到？是则进入口约束层。
2. 是否只是项目稳定事实？是则进项目事实层。
3. 是否包含条件判断和执行步骤？是则进 Skill。
4. 是否需要访问外部系统？是则考虑 MCP。
5. 是否能够通过脚本确定性执行？是则优先自动化，不只写文档。
