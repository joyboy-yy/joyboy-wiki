# 工具选择路由

工具选择从“缺少什么证据”开始，而不是从“有哪些工具”开始。每次调用前先问：这个输出能改变什么决策？不能改变就停止。

## 通用路由

| 证据缺口 | 首选能力 | 升级条件 |
|---|---|---|
| 不知道文件路径 | Glob | 命中后 Read |
| 已知符号、字符串或接口标识 | Grep | 读取命中及必要调用链 |
| 跨多个区域理解代码库 | Explore Task | 需要精确实现时回到 Grep/Read |
| 修改文本文件 | Apply Patch | 修改后检查 diff 和最小验证 |
| Git、构建、测试、运行 | Bash 调用项目 task | 边界变化时按测试策略升级 |
| 需要用户选择或缺少关键需求 | Question | 得到答案后继续，不反复询问 |
| 普通网页事实 | Web Fetch | 需要保存网页时加载 URL-to-Markdown Skill |
| Word/PDF/PPT/Excel | 对应 Office Skill | 只处理对应格式时加载 |
| 一次性浏览器流程 | `playwright-cli` Skill | 需要根因诊断时增加 Chrome DevTools |
| 浏览器运行时、网络、性能 | Chrome DevTools | 请求产生契约假设时增加项目 OpenAPI |
| 稳定浏览器回归 | 项目 Playwright Test | 失败原因不明时增加 Chrome DevTools |
| 稳定实体与关系 | Memory MCP | 长文和项目记录写入 Obsidian |

## 项目能力路由

项目可以提供额外 MCP、Skills 和 Taskfile。Agent 进入项目后先加载项目入口和能力声明，不把个人工具名称强加给团队规则。

```text
API 契约缺口 -> 项目 OpenAPI MCP（若配置）
真实数据库缺口 -> 项目数据库 MCP（默认只读）
源码实现缺口 -> 精确 Grep / Read
用户流程缺口 -> Playwright CLI 或项目 E2E
运行时根因缺口 -> Chrome DevTools
变更验证缺口 -> 项目测试策略与 task 命令
```

示例项目：[[工作/cssz/house-platform-backend/00-项目工程架构#Agent 工具层|house-platform-backend Agent 工具层]]。

## 跨工具过渡

- Chrome 捕获具体失败请求后，只有存在契约疑问才进入 OpenAPI。
- OpenAPI 得到 path、method、operation 或 schema 后，用这些标识精确定位源码。
- Mapper 源码得到表名和 SQL 假设后，再针对性检查数据库 schema、index 和数据。
- Playwright 驱动流程失败但信息不足时，使用 Chrome 查看 Console 和目标请求，不盲目重试。
- 代码修改完成后进入测试决策，不因已有构建结果而跳过行为验证。

## 停止条件

- 当前证据已经回答问题。
- 下一工具不会改变实现、诊断或验证决策。
- 工具不可用且没有等价证据来源，此时报告缺口。
- 操作将进入写数据、发布、删除或真实外部调用，但尚未获得授权。

## 反模式

- 每个任务先列出全部 MCP、sources、tags 或表。
- 面对契约或运行时问题先宽泛 Grep/Read 整个仓库。
- 同时启动 Playwright CLI、Chrome、OpenAPI 和数据库工具，却没有独立假设。
- 用 MCP 调用数量代替问题解决证据。
- 用一次手工点通声称存在稳定回归覆盖。
