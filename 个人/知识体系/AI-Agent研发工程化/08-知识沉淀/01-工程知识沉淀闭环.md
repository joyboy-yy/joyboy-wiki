# 工程知识沉淀闭环

知识沉淀不是把每次对话全部保存，而是把可复用判断放到正确层级，并保留证据来源。

## 四类知识

| 类型 | 示例 | 推荐去向 |
|---|---|---|
| 项目事实 | 模块、端口、数据库、依赖边界 | 项目 `PROJECT.md` |
| 团队规则 | 提交、测试、编码和安全约束 | `AGENTS.md`、专项规则、`TESTING.md` |
| 可复用流程 | 测试编排、排障、代码审查 | Skill |
| 跨项目方法论 | 上下文管理、MCP 治理、成熟度模型 | 个人知识库 |

## 沉淀流程

```text
任务结果
  -> 是否只是一次性事实？不保存或写日志
  -> 是否改变项目真实状态？更新项目文档
  -> 是否形成重复判断流程？更新 Skill
  -> 是否跨项目复用？进入个人知识库
  -> 是否需要团队共识？评审后转团队资产
```

## 笔记质量标准

- 有明确问题域和适用范围。
- 有权威来源或验证日期。
- 结论与执行步骤分开。
- 使用双链引用，不复制完整段落。
- 标明当前状态：草稿、已验证、长期有效、已废弃。
- 涉及工具时说明替代方案，避免工具锁定。

## 结果记录

一次重要任务建议记录：

- 背景与目标。
- 关键约束和决策。
- 修改范围。
- 验证证据。
- 失败尝试和根因。
- 可复用方法。
- 后续演进项。

## 维护机制

- 每月检查入口文档和 Skills 是否重复。
- 技术栈升级时检查事实来源和测试能力。
- MCP 变化时只更新个人配置与工具路由。
- 已过时笔记标记 deprecated，并指向替代内容。
- 高频复盘主题升级为模板或 Skill。

## 与项目知识的关系

个人知识库保存“如何建设 Agent 工程体系”；项目仓库保存“该项目当前如何工作”。两者用链接或来源字段关联，不复制敏感项目细节。
