# 项目规则文档分层

规则文件的目标不是覆盖所有知识，而是以最少上下文把 Agent 路由到正确事实来源。

## 推荐职责

| 文档 | 单一职责 | 不应包含 |
|---|---|---|
| `AGENTS.md` / `CLAUDE.md` | 自动加载入口、硬约束、条件阅读路由 | 命令大全、框架教程、长示例 |
| `PROJECT.md` | 稳定项目事实、架构、模块、端口、数据约束 | 个人 MCP、Agent 工具偏好 |
| `TESTING.md` | 变更分类、验证选择、测试语义、结果报告 | 项目架构和实现细则 |
| 语言/框架规则 | Java、前端、SQL 等专项规范 | 全局入口和工具配置 |
| `Taskfile.yml` | 可执行命令及参数 | 测试策略和架构说明 |

## 单一事实来源

- 版本：依赖清单和锁文件。
- 命令：任务编排文件及 `task -l`。
- 运行配置：应用配置文件。
- 数据库：实际 schema 和版本化 SQL。
- 验证策略：`TESTING.md`。
- 个人工具路由：本地 Skills。

## 做减法的方法

1. 找出跨文档重复出现的主题。
2. 为每个主题确定唯一权威文档。
3. 入口只保留一句条件路由，不复制详细规则。
4. 删除静态命令表，改为指向可执行任务列表。
5. 保留高代价且非通用的硬约束，如禁止误提交测试或密钥。
6. 用镜像一致性检查替代人工记忆。

## 反模式

- 在所有入口重复同一套 Java 规范。
- 把 MCP 工具列表和本机路径写进团队 `PROJECT.md`。
- 文档写“完整命令表”，但实际命令已经变化。
- 中文镜像被当作第二套规则独立维护。
- 用越来越长的提示词补偿缺失的脚本和测试。

## 评审问题

- 删除这段后，Agent 能否通过明确链接找到它？
- 规则是否描述事实，还是描述个人偏好？
- 内容能否由源码或命令自动发现？
- 同一规则是否在三个以上位置出现？
