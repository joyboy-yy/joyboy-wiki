# 成熟度模型与演进路线

## 五级成熟度

| 级别 | 特征 | 主要问题 |
|---|---|---|
| L0 工具使用 | 临时提示词、手工复制上下文 | 不稳定、不可复用 |
| L1 项目规则 | 有 AGENTS/CLAUDE 和基础约束 | 规则重复、命令漂移 |
| L2 标准工作流 | 有 PROJECT、TESTING、Task、分层测试 | 个人工具仍零散 |
| L3 能力编排 | Skills 按条件路由 MCP、CLI 和测试 | 缺少量化与治理 |
| L4 持续优化 | 有 CI/本地门禁、指标、复盘和知识闭环 | 重点转向组织推广 |

## 当前建设重点

1. 精简自动加载入口，建立条件阅读。
2. 明确项目事实、测试策略和个人工具边界。
3. 建立测试编排 Skill，阻止过度测试和工具滥用。
4. 统一项目命令入口，保证本地可重复执行。
5. 建立个人知识域和可复用模板。

## 下一阶段路线

### 短期

- 为新项目建立接入检查清单。
- 对核心 Skills 做无 Skill/有 Skill 对照验证。
- 清理团队文档中的个人 MCP 配置。
- 记录 Agent 误判、返工和无效工具调用。

### 中期

- 增加文档镜像、链接和命令存在性检查。
- 建立统一验证报告格式。
- 将稳定个人 Skills 抽象为跨项目用户级 Skills。
- 为高风险 API、数据库和页面建立可重复冒烟。

### 长期

- 接入 CI，共用本地 `task` 命令。
- 建立 Agent 任务质量指标和回归集。
- 对团队 Skills 做版本、评审和发布治理。
- 建立项目知识检索、架构图和决策记录体系。

## 评估指标

- 首次实现通过率。
- 平均返工轮次。
- 无效工具调用数。
- 聚焦测试与全量测试耗时比。
- 规则重复率和入口 token 数。
- 测试虚报或未验证风险遗漏次数。
- 新成员/新 Agent 接入项目所需时间。

## 终局判断

工程化成熟的标志不是 Agent 使用了多少工具，而是它能在正确上下文中选择最少必要能力，并用可重复证据完成任务。
