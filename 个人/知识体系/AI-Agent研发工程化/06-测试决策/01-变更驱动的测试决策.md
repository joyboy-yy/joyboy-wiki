# 变更驱动的测试决策

测试编排不是“每次跑全量”，而是识别变更能力和跨越边界，选择真正能发现目标缺陷的最小验证。

## 决策维度

1. **行为变化**：什么输入、状态或契约发生变化？
2. **影响范围**：单函数、单模块、跨模块还是全栈？
3. **边界数量**：进程、API、数据库、浏览器、外部服务。
4. **失败代价**：普通显示问题、数据错误、权限漏洞还是资金风险？
5. **可重复性**：是否存在稳定自动化测试层？

## 测试选择矩阵

| 变更类型 | 最小验证 | 升级条件 |
|---|---|---|
| 纯计算或校验逻辑 | 聚焦单元测试 + 模块编译 | 多消费者或共享公共逻辑 |
| Service 编排 | Mock 外部边界的单元测试 | 事务或真实接线变化 |
| Controller / DTO / VO | Web 测试 + 模块编译 | 前端消费者或公开契约变化 |
| Mapper / SQL / 事务 | 聚焦集成测试 + 数据库语义检查 | schema、回滚或真实数据相关 |
| 前端类型和工具函数 | 类型构建 + 聚焦测试 | 影响页面交互 |
| 页面、路由、权限、表单 | 前端构建 + 浏览器流程 | API 或登录态存在不一致 |
| 依赖、构建、运行配置 | 直接受影响任务 | 打包、启动或跨模块解析变化 |
| 文档 | 镜像、链接、示例、命令名 | 文档改变真实命令行为 |

## 升级门禁

- 单元测试通过不代表数据库 SQL 正确。
- 编译通过不代表行为测试通过。
- OpenAPI 一致不代表接口运行正常。
- 页面手工点通不代表有持久回归覆盖。
- 没有实际运行 `*IT`，不得声称集成测试通过。
- 测试被忽略或只存在本地，不能声称仓库具有持久覆盖。

## 输出契约

每次验证报告至少包含：

- 执行的准确命令。
- 测试数量、失败、错误、跳过。
- 构建和行为测试分别报告。
- 使用的浏览器、API、数据库诊断。
- 未执行的验证及原因。
- 剩余风险和建议下一步。

## Skill 化

测试矩阵属于团队策略；工具路由和个人可用 MCP 则放入个人测试编排 Skill。Skill 应阻止“所有工具都调用”和“聚焦测试后仍机械全量测试”。
