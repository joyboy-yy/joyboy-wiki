# 无 CI 场景的验证策略

没有 CI 不等于不需要测试，而是本地验证成为唯一自动化证据，Agent 的验证真实性更重要。

## 核心约束

- 完成任务前必须实际运行所需本地检查。
- 不得用“理论上可运行”代替执行结果。
- 测试不存在、被忽略或环境不可用时必须明确说明。
- 本地单元测试可提升当前工作区质量，但不能代表新 clone 具备覆盖。
- 提交前检查 staged 文件，避免测试、密钥和个人配置误提交。

## 推荐分层

| 层级 | 日常用途 | 频率 |
|---|---|---|
| L0 静态检查 | 编译、类型、格式和依赖解析 | 每次相关变更 |
| L1 聚焦测试 | 证明当前行为变化 | 每次行为变更 |
| L2 模块测试 | 共享逻辑和模块边界 | 按风险 |
| L3 集成测试 | 数据库、事务、外部接线 | 边界变化时 |
| L4 浏览器/API 冒烟 | 用户可见和全栈流程 | 页面/API 变化时 |
| L5 全量构建 | 发版、依赖和跨模块变化 | 低频 |

## 本地证据保存

- 项目任务统一输出结构化结果并归档完整日志。
- 最终回复记录命令、结果和日志位置。
- 失败时保留最小复现步骤，而不是只保留截图。
- 对高风险功能建立可重复执行的本地脚本。

## 测试不提交时的权衡

优点：符合团队仓库策略，不增加测试维护负担。

代价：

- 新 clone 无法复用测试。
- 其他成员无法共享回归覆盖。
- Agent 需要重新生成或依赖个人工作区。

因此应区分“本地测试帮助当前任务”与“仓库具有长期质量门禁”，不能混为一谈。

## 未来接入 CI

优先迁移稳定、高价值、无环境依赖的测试；再接入契约和浏览器冒烟。CI 命令应复用本地 `task` 能力，避免本地与流水线两套逻辑。
